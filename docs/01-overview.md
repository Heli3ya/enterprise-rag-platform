# ۰۱ — معرفی و نمای کلی

## ۱. مسئله

سازمان‌ها حجم زیادی سند داخلی دارند (قوانین، رویه‌ها، مستندات فنی، قراردادها) که پیدا کردن پاسخ در آن‌ها کند و وابسته به حافظه افراد است. جست‌وجوی کلیدواژه‌ای هم پاسخ «مفهومی» نمی‌دهد و منبع پاسخ را شفاف نمی‌کند.

این پروژه یک لایه دانش سازمانی می‌سازد که:

- اسناد را در سطح **سازمان (Tenant)** و **دپارتمان** نگه می‌دارد.
- به زبان طبیعی جست‌وجو می‌کند (معنایی + کلیدواژه‌ای).
- پاسخ را **فقط از اسناد مجاز همان کاربر** تولید می‌کند.
- برای هر جمله، شماره Chunk منبع را برمی‌گرداند تا قابل راستی‌آزمایی باشد.

## ۲. قابلیت‌ها

| قابلیت | وضعیت | توضیح |
|---|---|---|
| آپلود PDF / DOCX / DOC / TXT | پیاده‌سازی شده | حداکثر ۵ مگابایت، تشخیص MIME واقعی با libmagic |
| استخراج متن و تکه‌بندی | پیاده‌سازی شده | Chunk توکنی ۴۰۰ توکنی با ۱۰٪ هم‌پوشانی |
| Embedding و ایندکس برداری | پیاده‌سازی شده | مدل `intfloat/multilingual-e5-small` با ۳۸۴ بُعد |
| جست‌وجوی ترکیبی | پیاده‌سازی شده | وزن ۰٫۷ معنایی + ۰٫۳ کلیدواژه‌ای |
| Rerank | پیاده‌سازی شده | Cross-Encoder روی ۵ کاندید برتر |
| پاسخ RAG با Citation | پیاده‌سازی شده | ارجاع درون‌متنی `[chunk_id]` |
| پاسخ جریانی (SSE) | پیاده‌سازی شده | رویدادهای `token`، `citations`، `error`، `done` |
| چند-مستأجری | پیاده‌سازی شده | فیلتر Tenant در مدل، احراز هویت و کوئری‌ها |
| نقش‌ها | پایه | `Admin` و `Member` |
| تاریخچه جست‌وجو | پیاده‌سازی شده | `SearchQuery` و `QueryResult` |
| Audit Log | پیاده‌سازی شده | اقدامات `UPLOAD`، `DELETE`، `SEARCH`، `RAG_QUERY` |
| محدودیت نرخ | پیاده‌سازی شده | چت بر اساس نقش، آپلود ۱۰ در ساعت، Nginx لایه شبکه |
| پنل تحلیلی ادمین | پیاده‌سازی شده | آمار سند، جست‌وجو و دپارتمان |
| مدیریت کاربران از UI | پیاده‌سازی نشده | فعلاً از Django Admin |
| تاریخچه مکالمه | پیاده‌سازی نشده | `conversation_id` ذخیره نمی‌شود |

## ۳. اجزای سیستم

### Django API

قلب سیستم است: احراز هویت، مجوزدهی، مدیریت اسناد، هم‌ارزی جست‌وجو، ساخت Prompt، فراخوانی سرویس AI، ثبت Audit و ارائه متریک.

نقاط ورود مهم:

- `config/settings.py` — پیکربندی
- `config/urls.py` — مسیرهای ریشه
- `api/views.py` — جست‌وجو، RAG، چت، تحلیل
- `documents/views.py` — آپلود، وضعیت و حذف سند
- `api/services.py` — منطق بازیابی و ساخت Prompt

### سرویس AI (FastAPI)

مدل‌ها را یک‌بار در فرآیند بارگذاری می‌کند و چهار سرویس ارائه می‌دهد:

- `POST /api/embed/` — تولید بردار متن
- `POST /api/vector-search/` — جست‌وجوی نزدیک‌ترین همسایه در pgvector
- `POST /api/rerank/` — امتیازدهی مجدد با Cross-Encoder
- `POST /api/llm/` و `/api/llm/stream/` — تولید پاسخ با Ollama یا API سازگار با OpenAI

این سرویس در Compose روی میزبان منتشر نمی‌شود و فقط از شبکه داخلی در دسترس است.

### PostgreSQL + pgvector

نگهداری Tenant، کاربر، دپارتمان، سند، Chunk، Embedding، تاریخچه جست‌وجو، Audit و تنظیم محدودیت نرخ.

ایندکس‌های کلیدی:

- HNSW روی `embedding_vector` با عملگر کسینوسی
- GIN روی `content` برای جست‌وجوی متنی
- ایندکس یکتا روی `(document, chunk_index)`

### Redis و Celery

Redis دو نقش دارد: کش (DB 1) و Broker/Backend سلری (DB 0). Celery پردازش سنگین سند را از مسیر درخواست HTTP جدا می‌کند.

### Next.js

سه صفحه اصلی: ورود، صفحه اصلی (آپلود + چت) و داشبورد ادمین.

## ۴. جریان‌های اصلی

### جریان آپلود و ایندکس

```text
کاربر ──POST /api/documents/──> Django
                                  ├─ بررسی اندازه، MIME، دپارتمان و Tenant
                                  ├─ ذخیره فایل در media/documents/tenant_<id>/
                                  ├─ ثبت Document با وضعیت Pending
                                  ├─ ثبت AuditLog(UPLOAD)
                                  └─ process_document.delay()
                                            │
                                            ▼
                                     Celery Worker
                                      ├─ status = Processing
                                      ├─ استخراج متن (PDF/DOCX/TXT)
                                      ├─ تکه‌بندی ۴۰۰ توکنی
                                      ├─ ذخیره Chunkها
                                      ├─ صف‌بندی batchهای ۱۶تایی Embedding
                                      └─ status = Indexed (پس از کامل شدن همه بردارها)
```

جزئیات: [06-document-pipeline.md](06-document-pipeline.md)

### جریان جست‌وجو

```text
کاربر ──POST /api/query/search/──> Django
                                     ├─ hybrid_search()
                                     │    ├─ سرویس AI: جست‌وجوی برداری (tenant + department)
                                     │    ├─ PostgreSQL: جست‌وجوی کلیدواژه‌ای
                                     │    ├─ نرمال‌سازی و ادغام وزنی
                                     │    └─ Rerank پنج کاندید برتر
                                     ├─ بازبینی مالکیت Chunkها در دیتابیس
                                     ├─ ذخیره SearchQuery و QueryResult
                                     └─ ثبت AuditLog(SEARCH)
```

### جریان چت

```text
کاربر ──POST /api/chat/ask/──> Django
                                 ├─ محدودیت نرخ بر اساس نقش
                                 ├─ hybrid_search()
                                 ├─ ساخت Prompt با شناسه Chunkها
                                 ├─ Stream از LLM
                                 └─ SSE: token... → citations → done
```

جزئیات: [07-rag-pipeline.md](07-rag-pipeline.md)

## ۵. مدل دسترسی در یک نگاه

| موضوع | قاعده فعلی |
|---|---|
| Tenant کاربر | از `User.tenant` گرفته می‌شود؛ کاربر بدون Tenant معتبر رد می‌شود |
| دپارتمان سند | سند همیشه به یک دپارتمان از همان Tenant تعلق دارد |
| آپلود | کاربر باید عضو دپارتمان مقصد باشد، یا Admin باشد |
| مشاهده سند | Admin همه اسناد Tenant؛ Member فقط اسناد دپارتمان خود |
| حذف سند | آپلودکننده یا Admin |
| جست‌وجو | فقط Chunkهای دپارتمان کاربر (و اسناد `is_public` در فیلتر نهایی) |
| تحلیل و Audit | فقط Admin و فقط در محدوده Tenant خودش |

جزئیات و شکاف‌ها: [08-security.md](08-security.md)

## ۶. وضعیت و انتظارات

این پروژه یک پیاده‌سازی قابل اجرا و تست‌شده از یک پلتفرم RAG سازمانی است، اما چند نکته را باید بدانید:

- پوشش تست روی بک‌اند متمرکز است؛ فرانت‌اند تست E2E محدود دارد.
- برخی تصمیم‌ها (نقش‌ها، دامنه جست‌وجو، صفحه‌بندی) ساده‌سازی شده‌اند.
- استقرار Production نیاز به سخت‌سازی شبکه، HTTPS، پشتیبان‌گیری و ظرفیت‌سنجی دارد.
