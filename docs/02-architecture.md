# ۰۲ — معماری

## ۱. نمای کلی

سیستم از چهار فرآیند مستقل تشکیل شده که از طریق HTTP و شبکه داخلی Docker با هم صحبت می‌کنند:

```text
┌──────────────────────────────────────────────────────────────────┐
│                        مرورگر کاربر                              │
│                   Next.js (توسعه :3000)                           │
└───────────────────────────┬──────────────────────────────────────┘
                            │ HTTPS/HTTP
┌───────────────────────────▼──────────────────────────────────────┐
│ Nginx :80  ── rate limit عمومی 10r/s، آپلود 2r/m، بدنه حداکثر 6m │
└───────────────────────────┬──────────────────────────────────────┘
                            │ proxy_pass 127.0.0.1:8000
┌───────────────────────────▼──────────────────────────────────────┐
│ Django + DRF (Gunicorn, 2 workers)                                │
│  ├─ TenantJWTAuthentication                                       │
│  ├─ TenantMiddleware                                              │
│  ├─ ViewSet/View های اسناد، جست‌وجو، RAG، تحلیل                  │
│  └─ Celery client                                                 │
└───────┬───────────────────────┬──────────────────────┬───────────┘
        │ SQL                   │ HTTP داخلی            │ صف
        ▼                       ▼                       ▼
┌───────────────┐      ┌──────────────────┐      ┌──────────────┐
│ PostgreSQL 16 │◄─────│ FastAPI AI :8001 │      │ Redis 7      │
│ + pgvector    │      │ Embed/Rerank/LLM │      │ cache + queue│
└───────────────┘      └────────┬─────────┘      └──────┬───────┘
                                │                        │
                                ▼                        ▼
                    ┌────────────────────┐      ┌──────────────────┐
                    │ Ollama / OpenAI-   │      │ Celery Worker    │
                    │ compatible LLM     │      │ پردازش اسناد     │
                    └────────────────────┘      └──────────────────┘
```

## ۲. مسئولیت‌ها و مرزها

| جزء | مسئولیت | مسئولیت ندارد |
|---|---|---|
| Django | هویت، مجوز، قواعد Tenant، CRUD سند، هم‌ارزی، Audit | استنتاج مدل، محاسبه بردار |
| FastAPI | Embedding، Vector Search، Rerank، فراخوانی LLM | تصمیم دسترسی، اعتبارسنجی کاربر |
| PostgreSQL | منبع حقیقت داده و بردار | منطق کسب‌وکار |
| Celery | پردازش غیرهم‌زمان و retry | تصمیم مجوز |
| Next.js | تجربه کاربری و نگهداری توکن | تصمیم امنیتی نهایی |
| Nginx | TLS termination (در صورت تنظیم)، محدودیت نرخ شبکه، پروکسی | احراز هویت |

**قاعده طلایی:** هر تصمیم دسترسی فقط در Django گرفته می‌شود. سرویس AI و نتایج آن هرگز به‌عنوان مرجع مجوز استفاده نمی‌شوند.

## ۳. لایه‌های بک‌اند

```text
config/          پیکربندی، URL ریشه، Celery app
  └── api/       منطق جست‌وجو، RAG، تحلیل، Audit، Throttle
  └── documents/ مدل سند، Chunk، Embedding، استخراج، وظایف Celery
  └── accounts/  کاربر سفارشی و احراز هویت JWT
  └── tenants/   Tenant و میان‌افزار
  └── departments/ دپارتمان و API
```

### مسیر یک درخواست نمونه

`POST /api/query/ask/`

1. `PrometheusBeforeMiddleware` شروع زمان‌سنجی.
2. `CorsMiddleware` بررسی Origin.
3. `AuthenticationMiddleware` کاربر Session را (در صورت وجود) تشخیص می‌دهد.
4. `TenantMiddleware` در صورت احراز هویت Session، `request.tenant` را ست می‌کند.
5. DRF با `TenantJWTAuthentication` توکن Bearer را اعتبارسنجی می‌کند و Tenant فعال را بررسی می‌کند.
6. View: `_tenant_required_response` وجود و فعال بودن Tenant را دوباره بررسی می‌کند.
7. Serializer ورودی را اعتبارسنجی می‌کند (`query_text`، `top_k`).
8. `generate_rag_answer` بازیابی و فراخوانی LLM را انجام می‌دهد.
9. `build_citations` مالکیت Chunkهای ارجاع‌شده را در دیتابیس بررسی می‌کند.
10. `create_audit_log` ثبت می‌شود و پاسخ JSON برمی‌گردد.

## ۴. چرا این معماری؟

### جداسازی سرویس AI

مدل‌های Embedding و Rerank حافظه و CPU قابل توجهی مصرف می‌کنند و بارگذاری آن‌ها در فرآیند Django، چرخه درخواست وب را کند و شکننده می‌کند. سرویس مستقل اجازه می‌دهد:

- مدل یک‌بار در هر پروسه بارگذاری شود.
- هم‌زمانی استنتاج با `threading.Semaphore(1)` کنترل شود.
- سرویس AI مستقل از Django مقیاس‌پذیر یا restart شود.

### pgvector به‌جای پایگاه برداری جداگانه

مزیت اصلی، **اتمی بودن فیلتر Tenant و جست‌وجوی برداری در یک کوئری** است:

```sql
WHERE d.tenant_id = %s
  AND d.department_id = ANY(%s)
ORDER BY e.embedding_vector <=> %s::vector
LIMIT %s
```

اگر بردارها در سیستم جداگانه‌ای بودند، باید نتیجه جست‌وجو به Django می‌آمد و دوباره فیلتر می‌شد؛ یعنی یا نشت داده ممکن بود یا هزینه هم‌ارزی دوگانه. اینجا فیلتر در همان کوئری SQL اعمال می‌شود و Django هم دوباره مالکیت را تأیید می‌کند (defense in depth).

### جست‌وجوی ترکیبی

جست‌وجوی صرفاً معنایی روی اسامی خاص، شماره قرارداد، کد خطا و اصطلاحات داخلی ضعیف است. جست‌وجوی صرفاً کلیدواژه‌ای هم مترادف و بازنویسی معنایی را نمی‌فهمد. ترکیب این دو با وزن ۰٫۷/۰٫۳ و سپس Rerank، تعادل بهتری می‌دهد.

### Celery برای پردازش سند

استخراج PDF و تولید Embedding می‌تواند ده‌ها ثانیه طول بکشد. انجام آن در چرخه درخواست باعث timeout و تجربه بد می‌شود. آپلود سریع پاسخ می‌دهد و وضعیت سند از `Pending` به `Processing` و سپس `Indexed` می‌رود.

## ۵. جریان داده و حالت‌ها

### وضعیت سند

```text
Pending ──> Processing ──> Indexed
                │
                └────────> Failed
```

- `Pending`: فایل ذخیره شده، وظیفه در صف است.
- `Processing`: استخراج و تکه‌بندی در حال انجام است.
- `Indexed`: تعداد Embeddingها با تعداد Chunkها برابر شده است.
- `Failed`: خطا در استخراج، تکه‌بندی یا تولید بردار؛ پیام خطا در Celery log است.

### وضعیت وظیفه

Celery با `autoretry_for=(Exception,)`، `retry_backoff=True` و حداکثر ۳ تلاش تنظیم شده است. در صورت شکست نهایی، سند `Failed` می‌ماند و باید دوباره پردازش شود (آپلود مجدد یا فراخوانی دستی وظیفه).

## ۶. مرزهای اعتماد

| مرز | داخل مرز | خارج مرز |
|---|---|---|
| مرورگر ↔ Django | توکن JWT، ورودی کاربر | — |
| Django ↔ FastAPI | شبکه داخلی Compose، بدون احراز هویت | اینترنت |
| FastAPI ↔ PostgreSQL | اعتماد کامل (دسترسی مستقیم SQL) | — |
| Django ↔ Redis | شبکه داخلی | اینترنت |
| ادمین ↔ Django Admin | Session + superuser | — |

نکته مهم: **FastAPI هیچ لایه احراز هویتی ندارد.** هر کسی که به پورت ۸۰۰۱ دسترسی داشته باشد می‌تواند با `tenant_id` دلخواه جست‌وجوی برداری انجام دهد. به همین دلیل در Compose این پورت منتشر نشده و باید در هر استقرار، دسترسی شبکه‌ای به آن محدود بماند.

## ۷. مقیاس‌پذیری

### گلوگاه‌های فعلی

| منبع | محدودیت | نشانه |
|---|---|---|
| سرویس AI | `Semaphore(1)` همه استنتاج‌ها را سریالی می‌کند | صف انتظار و افزایش latency |
| Celery | یک worker پیش‌فرض | پردازش کند صف اسناد |
| Gunicorn | ۲ worker با timeout 300s | اشباع در بار بالا |
| Rerank | فقط ۵ کاندید، فراخوانی HTTP جدا | latency اضافه در هر جست‌وجو |
| PostgreSQL | ایندکس HNSW با `m=16` | کاهش recall یا کندی با حجم بالا |

### مسیرهای بهبود (بدون تغییر معماری)

1. افزایش `--concurrency` سلری و جدا کردن صف Embedding از استخراج.
2. اجرای چند replica از `ai_service` و حذف/کاهش قفل استنتاج (با آگاهی از مصرف RAM).
3. کش نتایج جست‌وجوی پرتکرار در Redis.
4. افزایش `ef_search` در pgvector برای recall بهتر در ازای latency.
5. صفحه‌بندی و محدودسازی لیست اسناد.

## ۸. شکست‌ها و رفتار سیستم

| شکست | رفتار فعلی | اثر کاربر |
|---|---|---|
| AI Service down | `requests` خطا می‌دهد؛ View کد ۵۰۲ برمی‌گرداند | جست‌وجو و چت خطا می‌دهند |
| LLM timeout | `RuntimeError`؛ در SSE رویداد `error` | پاسخ ناتمام |
| Redis down | کش و صف از کار می‌افتد؛ آپلود در صف نمی‌نشیند | سند در `Pending` می‌ماند |
| Celery worker down | سند در صف می‌ماند | وضعیت `Pending` طولانی |
| Tenant غیرفعال | `AuthenticationFailed` در لایه احراز هویت | ۴۰۱ برای همه endpointها |
| فایل نامعتبر | Serializer خطای ۴۰۰ می‌دهد | پیام «Unsupported file type» |
