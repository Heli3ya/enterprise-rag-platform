# ۱۳ — محدودیت‌ها و بدهی فنی

این فهرست از خواندن کد فعلی استخراج شده است. هدف، شفاف‌سازی رفتار واقعی و اولویت‌بندی اصلاحات است، نه ارزیابی کیفیت کلی پروژه.

## ۱. اولویت‌بندی

| سطح | معنا |
|---|---|
| **بالا** | ریسک امنیتی/داده‌ای یا رفتار نادرست در مسیر اصلی |
| **متوسط** | اثر محصولی یا عملیاتی محسوس |
| **پایین** | بهبود کیفیت، نگهداشت‌پذیری یا تجربه توسعه |

## ۲. امنیت و حریم خصوصی

### ۲.۱. لیست اسناد در سطح Tenant است، نه دپارتمان — **بالا**

`DocumentUploadView.get_queryset` فقط `tenant_id` را فیلتر می‌کند. هر Member می‌تواند عنوان، دپارتمان، وضعیت و تاریخ همه اسناد سازمان را ببیند.

**پیشنهاد:** فیلتر بر اساس `department_id` برای Member، یا حداقل حذف فراداده حساس از `DocumentListSerializer`.

### ۲.۲. ناسازگاری اسناد `is_public` — **متوسط**

`_filter_tenant_search_results` اسناد `is_public=True` را مجاز می‌داند، اما `semantic_search` و `keyword_search` فقط `department_id` کاربر را می‌گردند. نتیجه: اسناد public دپارتمان‌های دیگر در عمل پیدا نمی‌شوند.

**پیشنهاد:** یکسان‌سازی شرط در هر سه لایه:

```python
Q(document__is_public=True) | Q(document__department_id=user.department_id)
```

### ۲.۳. سرویس AI بدون احراز هویت — **بالا (در صورت افشا)**

هر کسی با دسترسی به پورت ۸۰۰۱ می‌تواند با `tenant_id` دلخواه جست‌وجوی برداری انجام دهد و محتوای Chunkها را بخواند. در Compose پورت منتشر نشده، اما این کنترل فقط شبکه‌ای است.

**پیشنهاد:** شبکه داخلی + API key داخلی یا mTLS؛ لاگ کردن فراخوانی‌ها.

### ۲.۴. توکن در `localStorage` — **متوسط**

در برابر XSS آسیب‌پذیر است و هیچ CSP سخت‌گیرانه‌ای تنظیم نشده.

**پیشنهاد:** کوکی `HttpOnly` + `Secure` + `SameSite=Lax` و محافظت CSRF، یا حداقل CSP.

### ۲.۵. بدون rotation و blacklist برای refresh token — **متوسط**

اپ `token_blacklist` نصب است اما `SIMPLE_JWT` تنظیم نشده و rotation فعال نیست. refresh token تا یک روز قابل استفاده مجدد است.

**پیشنهاد:**

```python
SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=15),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    "ROTATE_REFRESH_TOKENS": True,
    "BLACKLIST_AFTER_ROTATION": True,
}
```

### ۲.۶. `/api/docs/`، `/api/schema/` و `/metrics/` عمومی — **متوسط**

ساختار API و آمار سیستم بدون احراز هویت در دسترس است.

**پیشنهاد:** محدودسازی به IP داخلی یا افزودن permission.

### ۲.۷. بدون اسکن بدافزار — **متوسط**

فقط MIME و اندازه بررسی می‌شود. فایل مخرب با MIME مجاز پذیرفته می‌شود.

**پیشنهاد:** ClamAV یا سرویس اسکن در مسیر آپلود.

### ۲.۸. لاگ Audit بدون متادیتا — **پایین**

فقط `user`، `action` و `timestamp` ثبت می‌شود؛ IP، User-Agent، شناسه سند و متن پرسش وجود ندارد. برای بررسی حادثه کافی نیست.

## ۳. رفتار محصول

### ۳.۱. سقف ۵ نتیجه برای Rerank — **متوسط**

```python
rerank_candidates = fused_results[:5]
```

`top_k` تا ۵۰ مجاز است، اما در عمل بیش از ۵ نتیجه برگردانده نمی‌شود.

**پیشنهاد:** `candidates = max(5, limit)` یا پارامتر قابل تنظیم.

### ۳.۲. `/api/search/` امتیاز ادغام‌شده برمی‌گرداند — **پایین**

این endpoint `result["score"]` را برمی‌گرداند، در حالی که `/api/query/search/` `rerank_score` را برمی‌گرداند. مقایسه دو خروجی گمراه‌کننده است.

### ۳.۳. تاریخچه مکالمه وجود ندارد — **متوسط**

`conversation_id` اجباری است اما در سرور استفاده یا ذخیره نمی‌شود. هر سؤال مستقل است و ارجاع به پیام قبلی («آن را بیشتر توضیح بده») کار نمی‌کند.

**پیشنهاد:** مدل `Conversation` و `Message`، یا حذف فیلد از قرارداد API تا انتظار نادرست ایجاد نکند.

### ۳.۴. کاربر بدون دپارتمان نمی‌تواند جست‌وجو کند — **متوسط**

`get_user_department_id` برای `department_id=None` مقدار `None` برمی‌گرداند و `hybrid_search` لیست خالی می‌دهد. این شامل Admin بدون دپارتمان هم می‌شود.

### ۳.۵. فرمت `.doc` پشتیبانی کامل ندارد — **متوسط**
MIME `application/msword` مجاز است، اما `python-docx` فرمت باینری قدیمی را باز نمی‌کند. کاربر فایل را آپلود می‌کند و سند `Failed` می‌شود.

**پیشنهاد:** حذف `.doc` از لیست مجاز یا استفاده از `antiword`/`LibreOffice` برای تبدیل.

### ۳.۶. بدون OCR — **متوسط**

PDF اسکن‌شده متن استخراج‌شدنی ندارد و در مرحله تکه‌بندی شکست می‌خورد.

### ۳.۷. بدون صفحه‌بندی — **پایین**

همه لیست‌ها کامل برمی‌گردند. با رشد تعداد اسناد، پاسخ سنگین و UI کند می‌شود.

### ۳.۸. بدون دکمه خروج — **پایین**

`clearUser` فقط `user` را پاک می‌کند و توکن‌ها باقی می‌مانند. برای خروج کامل باید `access_token` و `refresh_token` هم حذف شوند.

### ۳.۹. چت refresh خودکار توکن ندارد — **پایین**

`ChatWindow` از `fetch` مستقیم استفاده می‌کند و interceptor Axios را دور می‌زند. با توکن منقضی، `401` می‌گیرد.

### ۳.۱۰. آستانه ارتباط برای Rerank وجود ندارد — **متوسط**

دروازه شروع سرد فقط «صفر نتیجه» را می‌گیرد. اگر دپارتمان سند داشته باشد ولی پرسش کاملاً بی‌ربط باشد، `semantic_search` همچنان نزدیک‌ترین همسایه‌ها را برمی‌گرداند (HNSW همیشه چیزی برمی‌گرداند) و `rerank_score` آن‌ها ممکن است بسیار پایین باشد؛ در این حالت LLM با زمینه بی‌ربط فراخوانی می‌شود.

**پیشنهاد:** یک آستانه قابل تنظیم (مثلاً `RAG_MIN_RERANK_SCORE`) که نتایج زیر آن حذف شوند و اگر همه حذف شدند، همان مسیر `no_documents` با `reason=no_match` طی شود. باید با مجموعه ارزیابی کالیبره شود، چون cross-encoder امتیازهای خام و منفی هم تولید می‌کند.

## ۴. داده و نگهداشت‌پذیری

### ۴.۱. ناسازگاری `ROLE_CHOICES` — **متوسط**

```python
ROLE_CHOICES = (("Admin", "Admin"),)
role = models.CharField(..., default="Member")
```

`Member` در choices نیست. در Django Admin گزینه معتبر دیده نمی‌شود و ممکن است داده موجود با فرم هم‌خوان نباشد.

**پیشنهاد:**

```python
ROLE_CHOICES = (("Admin", "Admin"), ("Member", "Member"))
```

### ۴.۲. نام فایل یکتا نیست — **متوسط**

مسیر `documents/tenant_<id>/<filename>` است. دو سند با نام یکسان، فایل قبلی را بازنویسی می‌کنند.

**پیشنهاد:** پیشوند UUID یا هش محتوا در نام فایل.

### ۴.۳. امکان Embedding تکراری — **پایین**

`Embedding` قید یکتایی روی `chunk` ندارد و `POST /api/embeddings/create/` بدون `ignore_conflicts` درج می‌کند. اجرای مکرر، بردارهای تکراری می‌سازد و جست‌وجو را سنگین می‌کند.

**پیشنهاد:** `UniqueConstraint(fields=["chunk"])` و حذف/جایگزینی بردار قبلی.

### ۴.۴. حذف فایل در مسیرهای غیر-API — **پایین**

حذف از Django Admin یا shell، رکورد را پاک می‌کند اما فایل را روی دیسک باقی می‌گذارد.

**پیشنهاد:** `post_delete` signal یا مدیریت دوره‌ای فایل‌های یتیم.

### ۴.۵. تنظیم محدودیت نرخ سراسری است — **پایین**

`RateLimitConfig` یک رکورد `pk=1` است و per-tenant نیست. یک سازمان پرترافیک و یک سازمان کوچک، سهمیه یکسان دارند.

### ۴.۶. فایل یتیم سند راهنما هنگام Rollback — **پایین**

`ensure_onboarding_document` فایل راهنما را روی Storage می‌نویسد و بعد ردیف `Document` را ذخیره می‌کند، و کل این کار داخل تراکنش ساخت دپارتمان اجرا می‌شود (سیگنال `post_save`). اگر همان تراکنش بعداً Rollback شود، ردیف پاک می‌شود ولی فایل در `media/documents/tenant_<id>/` می‌ماند.

عملاً نادر است: تنها راهش خطا در همان تراکنش پس از ساخت راهنماست. همان راه‌حل مورد ۴.۴ (پاکسازی دوره‌ای فایل‌های یتیم) این را هم پوشش می‌دهد. نوشتن فایل در `transaction.on_commit` هم ممکن است، ولی `file_path` را تا لحظه Commit خالی می‌گذارد و به تغییر schema نیاز دارد — برای این سطح از ریسک توجیه ندارد.

## ۵. عملیات و استقرار

### ۵.۱. پورت‌های Django روی همه رابط‌ها — **متوسط**

```yaml
ports:
  - "8000:8000"
  - "18001:8000"
```

نگاشت دوم ظاهراً باقی‌مانده است. برای Production فقط Loopback لازم است.

### ۵.۲. فرانت‌اند در Compose نیست — **متوسط**

`frontend/` در `.dockerignore` حذف شده و سرویس Compose ندارد. استقرار فرانت‌اند کاملاً جداگانه و مستندنشده در Compose است.

### ۵.۳. Celery قبل از migrate بالا می‌آید — **متوسط**

`depends_on` فقط سلامت Postgres/Redis/AI را چک می‌کند، نه پایان migration سرویس Django. در اولین استقرار ممکن است worker قبل از آماده شدن schema شروع کند.

**پیشنهاد:** healthcheck برای Django یا اجرای migrate در یک job جداگانه.

### ۵.۴. `DEBUG` پیش‌فرض `True` — **متوسط**

```python
DEBUG = os.getenv("DJANGO_DEBUG", "True").lower() in (...)
```

در Compose روی `False` ست شده، اما اجرای بدون `.env` در حالت Debug بالا می‌آید. برای Production بهتر است پیش‌فرض `False` باشد.

### ۵.۵. CI فقط بک‌اند — **پایین**

فرانت‌اند lint/build/E2E در CI اجرا نمی‌شود. flake8 هم فقط `F821`/`F822` را بررسی می‌کند و آستانه coverage وجود ندارد.

### ۵.۶. فایل‌های باقی‌ماندهٔ محلی — **پایین**

این فایل‌ها بخشی از کد فعال نیستند و باعث سردرگمی می‌شوند:

```text
ervices.py .apiservices_tenant_backup.py
api/services_tenant_backup.py
api/views.py.before-recovery.bak
api/views.py.from-git.tmp
api/views.py.recovered.tmp
api_views_diff_review.txt
```

**وضعیت:** این فایل‌ها هرگز در مخزن نبودند — همه در `.gitignore` هستند (خطوط ۴۲ تا ۴۶) و فقط روی دیسک محلی باقی مانده بودند. در ۲۰۲۶-۱۱-۱۲ به `C:/tmp/rag-leftovers/` منتقل شدند. مهم‌ترینشان `api/services_tenant_backup.py` بود: نسخه‌ای قدیمی از `api/services.py` که دروازه شروع سرد را ندارد و هیچ‌جا import نمی‌شود؛ اگر روزی اشتباهی ویرایش یا کپی می‌شد، باگ برمی‌گشت.

## ۶. مسیر پیشنهادی اصلاح

### گام ۱ — بستن شکاف‌های امنیتی

1. محدود کردن لیست اسناد به دپارتمان.
2. یکسان‌سازی منطق `is_public`.
3. تنظیم `SIMPLE_JWT` با rotation.
4. محدودسازی docs/metrics.
5. حذف نگاشت پورت اضافی.

### گام ۲ — درست کردن رفتار اصلی

1. پارامتردار کردن تعداد کاندیدهای Rerank.
2. اصلاح `ROLE_CHOICES`.
3. یکتاسازی نام فایل.
4. تصمیم درباره `conversation_id` (پیاده‌سازی یا حذف).

### گام ۳ — بهبود کیفیت

1. صفحه‌بندی.
2. دکمه خروج.
3. متادیتای Audit.
4. اسکن بدافزار و OCR.
5. CI فرانت‌اند و آستانه coverage.

## ۷. نکته درباره این فهرست

این موارد از کد استخراج شده‌اند و ممکن است برخی از آن‌ها آگاهانه انتخاب شده باشند (مثلاً سادگی در برابر پیچیدگی). قبل از تغییر، با مالک محصول هم‌خوان کنید و برای هر مورد تست اضافه کنید.
