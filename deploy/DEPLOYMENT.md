# Enterprise RAG Platform — Deployment Guide

راهنمای نصب، پیکربندی، راه‌اندازی و نگهداری پلتفرم سازمانی جست‌وجوی هوشمند اسناد

## 1. Overview

این راهنما مراحل آماده‌سازی و استقرار Enterprise RAG Platform روی یک سرور Linux را توضیح می‌دهد.

اجزای اصلی سامانه عبارت‌اند از:

- **Django:** API اصلی، احراز هویت و مدیریت اسناد.
- **FastAPI AI Service:** پردازش هوشمند اسناد، Embedding، بازیابی و تولید پاسخ.
- **PostgreSQL + pgvector:** ذخیره‌سازی داده‌ها و بردارهای معنایی.
- **Redis:** صف و زیرساخت عملیات پس‌زمینه.
- **Ollama یا OpenAI-compatible API:** ارائه‌دهنده مدل زبانی.
- **Nginx:** پراکسی معکوس و محدودسازی نرخ درخواست‌ها.
- **Docker Compose:** اجرای سرویس‌ها و مدیریت وابستگی‌ها.

> این راهنما برای استقرار روی Linux VPS نوشته شده است. اجرای واقعی استقرار باید پس از بررسی منابع سرور و تنظیمات امنیتی انجام شود.

## 2. Hardware Requirements

نیاز واقعی به سخت‌افزار به تعداد کاربران هم‌زمان، حجم اسناد، مدل‌های Embedding و Reranking و ارائه‌دهنده LLM بستگی دارد.

اعداد زیر برآورد اولیه برای برنامه‌ریزی هستند، نه حداقل تضمین‌شده یا نتیجه بنچمارک پروژه.

| منبع | استفاده از LLM ابری | Ollama محلی |
|---|---|---|
| CPU | 4 vCPU برای شروع | 4 تا 8 vCPU برای شروع |
| RAM | 8 GB برای ارزیابی اولیه | 16 GB یا بیشتر برای ارزیابی اولیه |
| دیسک | 50 GB SSD برای شروع | 50 تا 100 GB SSD یا بیشتر، بسته به مدل و حجم داده |
| GPU | معمولاً لازم نیست | برای اجرای CPU الزامی نیست؛ برای استنتاج سریع‌تر ممکن است مفید باشد |

### Important considerations

- سرویس AI علاوه بر LLM، مدل‌های Embedding و Reranking را نیز بارگذاری می‌کند؛ بنابراین RAM مورد نیاز فقط به مدل زبانی محدود نیست.
- اجرای مدل محلی روی CPU ممکن است کند باشد. نیاز حافظه به اندازه مدل، Quantization و Context Length وابسته است.
- حجم فایل‌های اسناد، مدل‌ها، تصاویر Docker و داده‌های PostgreSQL به مرور افزایش پیدا می‌کند.
- برای استفاده سازمانی و تعداد کاربران بیشتر، پیش از تعیین منابع نهایی باید مصرف واقعی RAM، CPU، دیسک و زمان پاسخ اندازه‌گیری شود.
- اجرای هم‌زمان مدل محلی و سرویس‌های دیگر روی یک سرور کوچک ممکن است باعث فشار حافظه و کندی شود.

## 3. Prerequisites

پیش از استقرار، موارد زیر باید آماده باشند:

1. یک سرور Linux پشتیبانی‌شده، ترجیحاً Ubuntu Server LTS.
2. دسترسی SSH و کاربری با مجوز `sudo`.
3. Docker Engine و Docker Compose v2.
4. دسترسی شبکه برای دریافت تصاویر Docker و وابستگی‌های Python در زمان نصب اولیه.
5. دامنه و گواهی TLS برای ارائه سرویس عمومی از طریق HTTPS.
6. تنظیمات معتبر فایل `.env`.
7. فضای ذخیره‌سازی کافی برای پایگاه داده، اسناد و کش مدل‌ها.

برای بررسی Docker روی سرور:

```bash
docker --version
docker compose version
docker info
```

اگر Docker نصب نیست، آن را طبق مستندات رسمی Docker برای توزیع Linux سرور نصب کن. از اجرای اسکریپت‌های نصب ناشناس با دسترسی root خودداری کن.

## 4. Prepare the Project

کد پروژه را از مخزن خصوصی یا منبع مورد اعتماد خود روی سرور دریافت کن.

نمونه:

```bash
git clone <YOUR_PRIVATE_REPOSITORY_URL> enterprise-rag-platform
cd enterprise-rag-platform
```

مقدار `<YOUR_PRIVATE_REPOSITORY_URL>` را با آدرس واقعی مخزن جایگزین کن.

مطمئن شو فایل‌های زیر وجود دارند:

```text
Dockerfile
docker-compose.yml
requirements-django.txt
ai_service/Dockerfile
ai_service/requirements.txt
deploy/setup.sh
deploy/nginx.conf
```

فایل `.env` باید در ریشه پروژه قرار داشته باشد و نباید در Git عمومی یا مخزن بدون کنترل دسترسی قرار بگیرد.

## 5. Configure Environment Variables

در ریشه پروژه، فایل `.env` را ایجاد یا تنظیم کن.

متغیرهای اصلی عبارت‌اند از:

```dotenv
DB_NAME=enterprise_rag
DB_USER=enterprise_rag_user
DB_PASSWORD=REPLACE_WITH_A_STRONG_UNIQUE_PASSWORD
DB_HOST=postgres
DB_PORT=5432

DJANGO_SECRET_KEY=REPLACE_WITH_A_UNIQUE_SECRET
SENTRY_DSN=
SENTRY_FASTAPI_DSN=

LLM_PROVIDER=ollama
LLM_BASE_URL=http://ollama:11434/api
LLM_MODEL=qwen2.5:3b
LLM_API_KEY=
```

این مقادیر نمونه هستند. نام دیتابیس، کاربر، رمز و Secret Key را مطابق محیط واقعی تنظیم کن.

### Security requirements

- از رمزهای یکتا و قوی برای PostgreSQL استفاده کن.
- `DJANGO_SECRET_KEY` باید تصادفی، محرمانه و مخصوص همین محیط باشد.
- برای تولید Secret Key از مولد امن رمزنگاری استفاده کن.
- مقدارهای واقعی را در Git commit نکن.
- مجوز دسترسی فایل `.env` را روی سرور محدود کن:

```bash
chmod 600 .env
```

- فایل `.env` را در لاگ‌ها، پیام‌های خطا یا گزارش‌های عمومی چاپ نکن.
- `DEBUG` باید در محیط Production غیرفعال باشد.
- تنظیمات Allowed Hosts، دامنه و HTTPS باید با محیط واقعی هماهنگ شوند.
- از نگهداری رمزها و کلیدهای API در مخزن کد خودداری کن.

### Important: Django Allowed Hosts

در نسخه فعلی `docker-compose.yml`، مقدار `DJANGO_ALLOWED_HOSTS` برای `localhost`، `127.0.0.1` و `django` تنظیم شده است.

اگر از دامنه واقعی استفاده می‌کنی، پیش از استقرار باید این تنظیم را در `docker-compose.yml` به دامنه‌های مورد اعتماد تغییر دهی. برای نمونه، دامنه واقعی و نام سرویس را بر اساس محیط خود تنظیم کن.

تنظیم Allowed Hosts را با CORS اشتباه نگیر؛ این دو تنظیم کاربردهای متفاوتی دارند.

همچنین مطمئن شو تنظیمات امنیتی Django برای HTTPS و پراکسی معکوس با پیکربندی واقعی سرور هماهنگ‌اند.

## 6. Choose the LLM Provider

دو حالت اصلی پشتیبانی می‌شوند.

### Option A — Ollama (Local LLM)

در فایل `.env`:

```dotenv
LLM_PROVIDER=ollama
LLM_BASE_URL=http://ollama:11434/api
LLM_MODEL=qwen2.5:3b
LLM_API_KEY=
```

در این حالت، سرویس AI از نام سرویس `ollama` در شبکه داخلی Docker برای ارتباط با Ollama استفاده می‌کند.

مدل در مرحله آماده‌سازی از طریق سرویس `ollama-model-init` دریافت می‌شود.

**نکته:** پیش از انتخاب مدل، RAM، فضای دیسک و عملکرد CPU یا GPU سرور را بررسی کن. اندازه مدل و سرعت پاسخ به سخت‌افزار و تنظیمات مدل وابسته‌اند.

### Option B — OpenAI-Compatible API

در فایل `.env`:

```dotenv
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=https://YOUR_PROVIDER_HOST/v1
LLM_MODEL=YOUR_PROVIDER_MODEL
LLM_API_KEY=YOUR_PROVIDER_API_KEY
```

آدرس و نام مدل باید دقیقاً مطابق مستندات ارائه‌دهنده واقعی باشند. بعضی سرویس‌ها ممکن است مسیر API متفاوتی داشته باشند.

اگر سرویس انتخاب‌شده به API Key نیاز ندارد، مطابق قرارداد همان سرویس تنظیمش کن.

در این حالت، پروفایل Ollama لازم نیست و اسکریپت نصب آن را راه‌اندازی نمی‌کند.

> استفاده از API سازگار با OpenAI لزوماً به معنی استفاده از سرویس رسمی OpenAI نیست؛ هر ارائه‌دهنده‌ای که با قرارداد مورد انتظار کلاینت سازگار باشد ممکن است استفاده شود.

## 7. Validate the Configuration

قبل از شروع Build یا دانلود مدل، در ریشه پروژه اجرا کن:

```bash
bash deploy/setup.sh --check-only
```

این حالت باید تنظیمات Docker Compose را اعتبارسنجی کند، بدون اینکه تصاویر را Build کند، سرویسی راه بیندازد یا مدل دانلود کند.

اگر اعتبارسنجی موفق نبود، قبل از ادامه خطا را برطرف کن.

در صورت استفاده از Ollama، پروفایل مربوطه نیز بررسی می‌شود.

## 8. Deploy the Application

پس از تأیید تنظیمات، منابع سرور و دسترسی شبکه، اجرا کن:

```bash
bash deploy/setup.sh --apply
```

در حالت Ollama، اسکریپت پیش از ادامه از تو تأیید صریح `INSTALL` می‌خواهد؛ زیرا دانلود مدل می‌تواند فضای دیسک و حافظه قابل توجهی مصرف کند.

این مرحله:

1. تصاویر Django و AI Service را Build می‌کند.
2. PostgreSQL و Redis را راه‌اندازی می‌کند.
3. در حالت Ollama، سرویس محلی و مرحله آماده‌سازی مدل را اجرا می‌کند.
4. AI Service و Django را راه‌اندازی می‌کند.
5. وضعیت سرویس‌ها را نمایش می‌دهد.

اولین اجرا ممکن است به علت دریافت تصاویر Docker، نصب وابستگی‌ها و دانلود مدل‌های AI زمان‌بر باشد.

### Important limitations

- موفقیت اجرای اسکریپت به‌تنهایی سلامت کامل برنامه را تضمین نمی‌کند.
- وضعیت Healthcheck سرویس‌ها، لاگ‌ها و ارتباطات داخلی باید بررسی شوند.
- در Compose فعلی، اجرای Django شامل Migrationهای پایگاه داده است.
- پیش از هر استقرار مجدد، از پایگاه داده و فایل‌های آپلودشده نسخه پشتیبان تهیه کن.
- در صورت شکست Build یا شروع سرویس‌ها، علت را بررسی کن؛ اجرای مکرر بدون بررسی ممکن است فقط همان خطا را تکرار کند.

## 9. Verify the Services

پس از پایان اجرای اسکریپت، وضعیت سرویس‌ها را بررسی کن:

```bash
docker compose ps
```

برای مشاهده لاگ‌های اصلی:

```bash
docker compose logs --tail=100 django ai_service
```

برای PostgreSQL و Redis:

```bash
docker compose logs --tail=100 postgres redis
```

در صورت استفاده از Ollama:

```bash
docker compose --profile ollama ps
docker compose --profile ollama logs --tail=100 ollama
```

### Verify Django

اگر پورت Django روی میزبان منتشر شده و مسیر ریشه قابل دسترس است، می‌توانی اتصال HTTP را با این دستور بررسی کنی:

```bash
curl -i http://127.0.0.1:8000/
```

پاسخ مسیر ریشه Django الزاماً معیار سلامت برنامه نیست. برای بررسی Django از endpoint سلامت اختصاصی پروژه، در صورت تعریف‌شدن، استفاده کن.

### Verify AI Service

پورت `8001` در تنظیمات فعلی Compose روی میزبان منتشر نشده است. این تصمیم به جلوگیری از دسترسی مستقیم و غیرضروری به AI Service کمک می‌کند.

برای بررسی endpoint سلامت از داخل کانتینر اجرا کن:

```bash
docker compose exec -T ai_service python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8001/health', timeout=10).read().decode())"
```

این دستور فقط زمانی قابل اجراست که کانتینر `ai_service` در حال اجرا باشد. اگر سرویس اجرا نیست، ابتدا وضعیت و لاگ‌های آن را بررسی کن؛ برای مثال:

```bash
docker compose ps -a
docker compose logs --tail=200 ai_service
```

در سرویس AI، مسیر `/health` برای Healthcheck استفاده می‌شود. پاسخ موفق این endpoint به‌تنهایی تضمین نمی‌کند که مدل LLM قابل دسترس است؛ اتصال مدل و یک درخواست واقعی نیز باید جداگانه بررسی شود.

## 10. Configure Nginx

فایل `deploy/nginx.conf` در نسخه فعلی یک پیکربندی کامل Nginx است و پراکسی درخواست‌های API را به Django روی `127.0.0.1:8000` هدایت می‌کند.

این راهنما Nginx را به‌صورت سرویس نصب‌شده روی میزبان Linux در نظر می‌گیرد.

پس از نصب Nginx، ابتدا از تنظیمات موجود نسخه پشتیبان تهیه کن. سپس فایل را مطابق ساختار توزیع Linux در مسیر اصلی پیکربندی Nginx قرار بده؛ آن را بدون بررسی داخل فایل `sites-available` کپی نکن، چون ساختار فایل فعلی شامل بلوک‌های اصلی `events` و `http` است.

پس از تنظیم، پیکربندی را بررسی کن:

```bash
sudo nginx -t
```

در صورت موفقیت:

```bash
sudo systemctl reload nginx
```

### Network and port security

در `docker-compose.yml` فعلی، Django با نگاشت پورت `8000:8000` منتشر شده است. این نگاشت ممکن است پورت را روی تمام رابط‌های شبکه میزبان در دسترس قرار دهد.

برای Production، بهتر است پورت Django فقط روی Loopback میزبان منتشر شود، مگر اینکه دلیل مشخصی برای دسترسی مستقیم وجود داشته باشد.

برای نمونه، نگاشت زیر فقط پورت را روی رابط Loopback میزبان منتشر می‌کند:

```yaml
ports:
  - "127.0.0.1:8000:8000"
```

این تغییر را با دقت در `docker-compose.yml` اعمال و سپس اعتبارسنجی کن.

پورت‌های PostgreSQL، Redis و AI Service نباید بدون نیاز و کنترل دسترسی به اینترنت عمومی منتشر شوند.

پس از تغییر نگاشت پورت، مطمئن شو Nginx روی همان میزبان به `127.0.0.1:8000` دسترسی دارد.

## 11. HTTPS and Domain Configuration

فایل Nginx فعلی فقط HTTP روی پورت 80 را پیکربندی می‌کند و به‌تنهایی HTTPS فراهم نمی‌کند.

برای سرویس عمومی:

1. دامنه را به IP سرور متصل کن.
2. تنظیم Allowed Hosts را برای دامنه به‌روزرسانی کن.
3. TLS را با گواهی معتبر پیکربندی کن.
4. ریدایرکت HTTP به HTTPS و هدرهای مناسب را تنظیم کن.
5. فقط پورت‌های مورد نیاز، معمولاً 80 و 443، را از اینترنت در دسترس قرار بده.
6. پس از فعال‌سازی HTTPS، رفتار کوکی‌ها، CORS و تنظیمات امنیتی Django را بررسی کن.
7. تنظیمات پراکسی معکوس و تشخیص HTTPS در Django را متناسب با معماری واقعی بررسی کن.

تا زمانی که HTTPS و کنترل دسترسی شبکه تنظیم نشده‌اند، نباید سرویس را برای استفاده عمومی Production آماده فرض کرد.

## 12. Offline and On-Premise Operation

انتخاب `LLM_PROVIDER=ollama` به‌تنهایی به معنی اجرای کاملاً آفلاین کل سامانه نیست.

سرویس ممکن است در اجرای اولیه برای موارد زیر به شبکه نیاز داشته باشد:

- تصاویر Docker؛
- بسته‌های Python و وابستگی‌های سیستم؛
- وزن‌های مدل LLM؛
- مدل‌های Embedding و Reranking؛
- هر سرویس خارجی یا ارسال خطایی که در تنظیمات فعال باشد.

سرویس AI از کش Hugging Face در Volume به نام `ai_model_cache` استفاده می‌کند.

برای محیطی که نباید به اینترنت دسترسی داشته باشد:

1. تصاویر مورد نیاز را از قبل دریافت و در رجیستری داخلی یا آرشیو قابل اعتماد ذخیره کن.
2. وابستگی‌های Python و بسته‌های سیستم را پیشاپیش آماده کن.
3. مدل‌های Embedding و Reranking را دریافت و کش آن‌ها را آماده کن.
4. مدل Ollama را در محیط دارای دسترسی شبکه دریافت کن و Volume یا روش انتقال امن مدل را آماده کن.
5. از دسترس‌پذیری همه منابع در شبکه داخلی اطمینان حاصل کن.
6. پس از آماده‌سازی، دسترسی اینترنت را در محیط آزمایشی قطع و تست‌های واقعی را اجرا کن.

برای انتقال تصاویر می‌توان از `docker save` و `docker load` استفاده کرد؛ برای مثال:

```bash
docker save -o enterprise-rag-images.tar IMAGE_NAME
docker load -i enterprise-rag-images.tar
```

`IMAGE_NAME` باید با نام و تگ واقعی تصویر جایگزین شود. این نمونه به‌تنهایی تمام تصاویر مورد نیاز پروژه را بسته‌بندی نمی‌کند.

برای اجرای آفلاین، علاوه بر تصاویر برنامه، باید تصاویر پایگاه داده، Redis، Ollama در صورت استفاده، و تمام وابستگی‌های لازم در دسترس باشند. کش مدل‌های AI و مدل Ollama نیز باید جداگانه آماده و آزمایش شوند.

**اجرای آفلاین واقعی فقط پس از تست مستقل و موفق همه وابستگی‌ها تأیید می‌شود.**

## 13. Backups and Recovery

از موارد زیر نسخه پشتیبان تهیه کن:

- داده‌های PostgreSQL؛
- فایل‌های آپلودشده در Volume مربوط به `media_data`؛
- تنظیمات ضروری و محرمانه در مخزن امن؛
- مدل‌ها یا کش‌های لازم برای محیط آفلاین، در صورت نیاز.

نمونه پشتیبان‌گیری از PostgreSQL با استفاده از تنظیمات داخل کانتینر:

```bash
docker compose exec -T postgres sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  > database-backup.sql
```

این دستور را در محیطی اجرا کن که دسترسی نوشتن در مسیر مقصد را داشته باشد. برای پایگاه داده‌های حساس، رمزگذاری فایل پشتیبان و انتقال آن به محل ذخیره‌سازی جداگانه را نیز در نظر بگیر.

فایل خروجی را در محل امن با دسترسی محدود نگهداری کن. بسته به اندازه پایگاه داده، فضای کافی و سیاست سازمان، از روش‌های مناسب‌تر و پشتیبان‌گیری زمان‌بندی‌شده استفاده کن.

برای بازیابی، ابتدا در محیط آزمایشی صحت نسخه پشتیبان را بررسی کن. نسخه پشتیبان تنها زمانی قابل اتکاست که بازیابی آن نیز آزمایش شده باشد.

پشتیبان پایگاه داده به‌تنهایی شامل فایل‌های آپلودشده، مدل‌ها یا تمام تنظیمات عملیاتی نیست؛ برای بازیابی کامل، این موارد نیز باید پوشش داده شوند.

## 14. Troubleshooting

### Docker Compose configuration fails

- وجود `.env` و `docker-compose.yml` را بررسی کن.
- متغیرهای ضروری را تنظیم کن.
- مقادیر `LLM_PROVIDER`، `LLM_BASE_URL` و `LLM_MODEL` را بررسی کن.
- خطاهای خروجی `docker compose config` را برطرف کن.

### AI Service is unhealthy

```bash
docker compose ps -a
docker compose logs --tail=200 ai_service
```

علت‌های احتمالی شامل دانلود نشدن مدل‌های Embedding، کمبود RAM، دسترسی نداشتن به سرویس LLM یا خطاهای وابستگی است.

اگر کانتینر اصلاً ایجاد نشده باشد، ابتدا خروجی Build و اجرای اسکریپت استقرار را بررسی کن.

### Ollama model initialization fails

```bash
docker compose --profile ollama logs --tail=200 ollama
docker compose --profile ollama logs --tail=200 ollama-model-init
```

دسترسی شبکه، فضای دیسک، RAM و نام مدل را بررسی کن.

### Django cannot connect to PostgreSQL

```bash
docker compose logs --tail=100 postgres django
```

مطمئن شو `DB_HOST` داخل کانتینر Django به `postgres` اشاره می‌کند و مقادیر دیتابیس در `.env` با هم هماهنگ‌اند.

### Nginx returns 502

- وضعیت Django را بررسی کن.
- مطمئن شو پورت میزبان قابل دسترسی است.
- مقدار `proxy_pass` و پورت منتشرشده در Compose را بررسی کن.
- لاگ Nginx و Django را مقایسه کن.

### Build fails during package installation

خطای DNS، پراکسی یا دسترسی به مخازن بسته‌ها را بررسی کن. از خاموش‌کردن کنترل‌های امنیتی شبکه یا تغییر تصادفی تنظیمات پراکسی برای رفع خطا خودداری کن.

## 15. Maintenance and Scalability

برای نگهداری Production:

- مصرف CPU، RAM، دیسک و زمان پاسخ را پایش کن.
- سلامت PostgreSQL، Redis و AI Service را بررسی کن.
- حجم کش مدل‌ها، فایل‌های آپلودشده و لاگ‌ها را کنترل کن.
- سیاست نگهداری و بازیابی نسخه‌های پشتیبان داشته باش.
- دسترسی API و محدودیت نرخ درخواست‌ها را متناسب با بار واقعی تنظیم کن.
- برای افزایش بار، سرویس AI را بر اساس ظرفیت محاسباتی و مصرف حافظه ارزیابی کن.
- قبل از تغییر تعداد Workerهای Django یا افزایش هم‌زمانی، مصرف حافظه و بار پایگاه داده را اندازه‌گیری کن.
- برای حجم بالاتر اسناد، ایندکس‌های PostgreSQL و pgvector، زمان پردازش پس‌زمینه و سیاست ذخیره‌سازی را ارزیابی کن.

افزایش پیچیدگی زیرساخت، مانند افزودن Orchestrator یا سرویس‌های جدید، باید بر اساس نیاز واقعی و نتایج اندازه‌گیری انجام شود.

## 16. Production Readiness Checklist

قبل از استفاده واقعی، موارد زیر را بررسی کن:

- [ ] تنظیمات `.env` معتبر و محرمانه‌اند.
- [ ] Django در حالت Production و با Secret Key یکتا اجرا می‌شود.
- [ ] Allowed Hosts با دامنه واقعی هماهنگ است.
- [ ] دسترسی عمومی به PostgreSQL، Redis و AI Service محدود شده است.
- [ ] HTTPS فعال و گواهی معتبر است.
- [ ] سرویس‌های اصلی و وابستگی‌ها سالم هستند.
- [ ] یک درخواست واقعی به AI Service و LLM با موفقیت آزمایش شده است.
- [ ] مجوزهای کاربران و دسترسی به اسناد آزمایش شده‌اند.
- [ ] پشتیبان‌گیری و بازیابی پایگاه داده و فایل‌ها آزمایش شده‌اند.
- [ ] منابع سخت‌افزاری با بار مورد انتظار سازگارند.
- [ ] اگر اجرای آفلاین لازم است، قطع اینترنت و اجرای واقعی آزمایش شده است.

## 17. Important Limitations

این راهنما فرایند استقرار را مستند می‌کند، اما به‌تنهایی تضمین‌کننده آماده‌بودن Production نیست. اجرای موفق، سلامت سرویس‌ها، امنیت شبکه، صحت مجوزهای کاربران و قابلیت بازیابی باید در محیط واقعی بررسی شوند.

هرگونه تغییر در تنظیمات Docker Compose، Nginx یا محیط Production باید ابتدا در محیط آزمایشی اعتبارسنجی شود.

**وضعیت اعتبارسنجی:** راهنما باید در کنار تنظیمات واقعی پروژه بررسی شود. تا زمانی که استقرار روی Linux VPS و تست‌های عملی انجام نشده‌اند، نباید ادعا کرد که استقرار یا اجرای آفلاین در محیط واقعی تأیید شده است.
